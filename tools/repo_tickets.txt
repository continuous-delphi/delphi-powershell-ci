Title: Add Invoke-DelphiCodesign with Sign and Verify actions
Issue: #12
Status: closed
Labels: enhancement
Body:
Add code signing support to the CI module by bundling
`delphi-codesign-azure.ps1` and exposing `Invoke-DelphiCodesign` as a
public command with `Sign` and `Verify` pipeline actions.

## Design

Use the established engine pattern (like Build has MSBuild/DCCBuild,
Coverage has DelphiCodeCoverage/radCodeCoverage). The codesign engine
abstraction allows future signing providers beyond Azure Trusted Signing
(e.g. local certificate store, DigiCert, other cloud HSMs).

### Public command: Invoke-DelphiCodesign

Parameters following the `<Action><Param>` naming convention:

- `-CodesignAction` -- `Sign` or `Verify` (ValidateSet)
- `-CodesignEngine` -- `AzureTrustedSigning` (default, only engine for now)
- `-CodesignFiles` -- string array of files to sign (Sign action)
- `-CodesignFilePath` -- single file to verify (Verify action)
- `-CodesignSignToolPath` -- explicit signtool.exe path
- `-CodesignDlibPath` -- Azure.CodeSigning.Dlib.dll path
- `-CodesignMetadataPath` -- metadata.json path
- `-CodesignEnvFile` -- .env file for Azure credentials
- `-CodesignFormat` -- output format (object/text/json)

### Pipeline action: Codesign

JSON config (`delphi-ci.json`) support:

```json
{
  "action": "Codesign",
  "jobs": [
    {
      "name": "Sign release binaries",
      "codesignAction": "Sign",
      "files": ["projects/cli/Win32/Release/app.exe"],
      "envFile": ".env"
    },
    {
      "name": "Verify signatures",
      "codesignAction": "Verify",
      "filePath": "projects/cli/Win32/Release/app.exe"
    }
  ]
}
```

Title: Codesign Verify fails when job inherits Sign-only params (metadataPath/envFile/dlibPath)
Issue: #13
Status: closed
Labels: bug
Body:
`Invoke-DelphiCodesign` appends the bundled tool's Sign-only parameters
(`-DlibPath`, `-MetadataPath`, `-EnvFile`) to the tool invocation whenever
those values are non-empty -- regardless of the requested `-Action`. When a
Verify job carries any of those values, the call fails with:

    delphi-codesign-azure.ps1: Parameter set cannot be resolved using the
    specified named parameters.

## Root cause

The bundled tool `delphi-codesign-azure.ps1` scopes `-DlibPath`,
`-MetadataPath`, and `-EnvFile` to `ParameterSetName = 'Sign'` (they do not
apply to verification, which only reads the embedded Authenticode signature
via `signtool verify /pa`). That design is correct -- verify has no use for
the Dlib, Azure metadata, or credentials.

The defect is in the wrapper, `source/Public/Invoke-DelphiCodesign.ps1`
(lines 59-62), which appends all four path params unconditionally:

    if (-not [string]::IsNullOrEmpty($CodesignSignToolPath))  { ... }
    if (-not [string]::IsNullOrEmpty($CodesignDlibPath))      { ... -DlibPath ... }
    if (-not [string]::IsNullOrEmpty($CodesignMetadataPath))  { ... -MetadataPath ... }
    if (-not [string]::IsNullOrEmpty($CodesignEnvFile))       { ... -EnvFile ... }

`-SignToolPath` is safe because it belongs to both the Sign and Verify
parameter sets; only `-DlibPath`/`-MetadataPath`/`-EnvFile` break parameter-set
resolution on a Verify call.

## Trigger

Setting `metadataPath`/`envFile` at the Codesign action level (or in
`defaults.codesign`) is a natural config shape for a Sign+Verify pipeline.
The resolver merges action-level fields into every job, so the Verify job
inherits them and the run fails. A downstream Sign+Verify config
(radFormatterV2 `BuildSign-delphici.json`) hit this; the current workaround
is to scope those paths to the Sign job only.

## Fix

Guard the Sign-only args behind the action in
`source/Public/Invoke-DelphiCodesign.ps1`:

    if (-not [string]::IsNullOrEmpty($CodesignSignToolPath)) { $toolArgs.Add('-SignToolPath'); $toolArgs.Add($CodesignSignToolPath) }
    if ($Action -eq 'Sign') {
        if (-not [string]::IsNullOrEmpty($CodesignDlibPath))     { $toolArgs.Add('-DlibPath');     $toolArgs.Add($CodesignDlibPath) }
        if (-not [string]::IsNullOrEmpty($CodesignMetadataPath)) { $toolArgs.Add('-MetadataPath'); $toolArgs.Add($CodesignMetadataPath) }
        if (-not [string]::IsNullOrEmpty($CodesignEnvFile))      { $toolArgs.Add('-EnvFile');      $toolArgs.Add($CodesignEnvFile) }
    }

No change is required in the `delphi-codesign-azure` repo -- its parameter
sets are correct as-is.

Acceptance criteria:
- [ ] A Verify job that inherits metadataPath/envFile/dlibPath no longer fails parameter-set resolution
- [ ] Sign action still passes -DlibPath/-MetadataPath/-EnvFile through to the bundled tool
- [ ] Regression test in tests/pwsh/Invoke-DelphiCodesign.Tests.ps1 covers a Verify call with non-empty signing params
- [ ] Action-level codesign defaults work for a combined Sign+Verify pipeline
- [ ] All Pester tests pass

Title: Plumb explicit toolchain.rootDir / -ToolchainRootDir down to bundled tools' -RootDir
Issue: #14
Status: closed
Labels: enhancement
Body:
Add an explicit `toolchain.rootDir` (config) / `-ToolchainRootDir` (parameter)
that bypasses `delphi-inspect` registry resolution and passes the supplied
directory straight through to the bundled build tool's already-capable
`-RootDir`.

## Background / motivation

The module currently locates the Delphi compiler **exclusively through the
Windows registry**: `Invoke-DelphiBuild` builds inspect args
(`Invoke-DelphiBuild.ps1:71`), `Invoke-BuildPipeline` runs `delphi-inspect.ps1`
(`Invoke-BuildPipeline.ps1:21`), extracts `.result.installation.rootDir`
(`:31`), and forwards `@('-RootDir', $rootDir, ...) + $BuildArgs` (`:47`).

That makes the module unusable against **trimmed, non-installed,
non-registered per-version toolchains** -- e.g. the `rad-buildfiles-d<NN>`
folders (`G:\radprogrammer\...`) used by the older batch build system, which
have a `bin`/`lib` layout but no registry registration. There is no config key
or parameter to point the module at such a root.

The capability already exists one layer down: the bundled `delphi-msbuild.ps1`
and `delphi-dccbuild.ps1` **accept an explicit `-RootDir`** and give it
precedence over any piped inspect object (`Resolve-RootDir`). The gap is purely
that the CI surface never lets a caller supply that root.

## Concrete changes

**1. Schema -- `schemas/delphi-ci.schema.json` (124-134).**
The `toolchain` object is `"additionalProperties": false` with only `version`.
Add an optional `rootDir`:

    "rootDir": { "type": "string", "description": "Explicit Delphi installation root. When set, registry detection is skipped and this path is passed to the build tool's -RootDir." }

The object is referenced by `$ref` from every action with a toolchain, so one
edit covers them all.

**2. `Invoke-DelphiBuild` -- `source/Public/Invoke-DelphiBuild.ps1` (11, 71).**
Add a `[string]$ToolchainRootDir` parameter alongside `$Toolchain`. When it is
non-empty, skip building `$inspectArgs` and signal the pipeline to use the
explicit root. Precedence: `rootDir` wins over `version`; optionally warn if
both are supplied.

**3. `Invoke-BuildPipeline` -- `source/Private/Invoke-BuildPipeline.ps1` (21, 31, 47).**
When an explicit root is provided, **skip the inspect subprocess entirely** and
set `$rootDir` to the supplied path (after a `Test-Path` existence check), then
forward it the same way. Everything downstream is unchanged because the bundled
tools already honor `-RootDir`.

**4. Config flow -- `Invoke-DelphiCi` / `Resolve-DelphiCiConfig` / `Merge-ActionConfig`.**
Carry `toolchain.rootDir` through config merge (same merge semantics as
`toolchain.version`) and pass it to `Invoke-DelphiBuild -ToolchainRootDir`.

No change is required in the bundled build tools -- `-RootDir` is already
supported.

## Related considerations (call out, don't necessarily solve here)

- **Readiness gating is bypassed by design.** Skipping inspect also skips its
  registry / `EnvOptions.proj` readiness checks (`Get-MSBuildReadiness`) -- that
  is the point; a portable root will never pass those. Document that an explicit
  `rootDir` opts out of readiness validation and trusts the caller.
- **Bundled tools still source `rsvars.bat`** (`<RootDir>\bin\rsvars.bat`). The
  `rad-buildfiles-d<NN>` toolchains' rsvars have been made self-locating so this
  works for D11..D29; full coverage of roots that lack rsvars depends on the
  sibling `-SkipRsvars` feature requests filed against `delphi-dccbuild` /
  `delphi-msbuild` (separate repos).
- **Very old versions** (Delphi 2/3/4) have no registry `RootDir` at all, so an
  explicit `rootDir` is the only way the module could ever target them.

Acceptance criteria:
- [ ] `delphi-ci.json` validates with a `build` job whose `toolchain` has `rootDir` set (and no `version`)
- [ ] `Invoke-DelphiBuild -ProjectFile ... -ToolchainRootDir 'G:\radprogrammer\rad-buildfiles-d28.11-Alexandria'` builds without any registry lookup (inspect not invoked), passing that path as `-RootDir` to the chosen engine
- [ ] A non-existent `rootDir` fails fast with a clear error (not an empty-rootDir error from inspect)
- [ ] When `rootDir` is absent, behavior is byte-for-byte unchanged (registry path)
- [ ] `Invoke-DelphiCi` end-to-end: a pipeline whose build job specifies `toolchain.rootDir` builds against that folder
- [ ] Pester coverage for the explicit-root path (inspect skipped) and the fail-fast on missing root

Title: Array build params fail when more than one value is supplied (repeated -Param forwarding)
Issue: #15
Status: closed
Labels: bug
Body:
## Problem

`Invoke-DelphiBuild` forwards array parameters to the bundled tool as repeated
named arguments -- e.g. `foreach ($n in $Namespace) { $buildArgs += '-Namespace'; $buildArgs += $n }`
(same for `-UnitSearchPath`, `-IncludePath`, `-Defines`). Those args are passed
to the bundled `delphi-dccbuild.ps1` / `delphi-msbuild.ps1` via
`pwsh -NoProfile -NonInteractive -File ... @allBuildArgs` in `Invoke-BuildPipeline`.

Under `-File`, a `[string[]]` parameter cannot be specified more than once, so
any array param with 2+ values fails:

  delphi-dccbuild.ps1: Cannot bind parameter because parameter 'Namespace' is
  specified more than once. ... use the array syntax ... value1,value2,value3

Observed building a namespaced Delphi (10.3 Rio / 10.4 Sydney) project, which
needs several unit-scope namespaces (Winapi;System;...). A single value per
array param happens to work (one `-Namespace`), which is why existing
single-value tests/usage pass; multi-value never has.

Note: passing a single comma-/semicolon-joined string does NOT work either --
`pwsh -File` does not split it, and the bundled tools join their `[string[]]`
with `;`, so the delimiter ends up literal inside one `-NS`/`-U` token.

## Proposed

Forward array parameters so the bundled tool receives a real multi-element
array. Options:

- Invoke the bundled tool in-process by splatting a hashtable with array values
  (`& $buildToolPath @params`) instead of `-File @flatargs` (trade-off: loses
  the current separate-process isolation), OR
- Keep the subprocess but pass each array as a single delimited value and have
  the bundled tools split it into their `[string[]]` params.

Apply the chosen approach consistently for Namespace, UnitSearchPath,
IncludePath, and Defines, for both engines.

## Acceptance criteria

- [ ] A build with 2+ namespaces succeeds (each reaches dcc32 as a distinct `-NS` entry)
- [ ] A build with 2+ unit search paths / include paths / defines succeeds for both engines
- [ ] Single-value array params continue to work
- [ ] A test exercises the real bundled-tool invocation (not a mock) with multi-value arrays

Title: Surface DCCBuild -NoConfig through Invoke-DelphiBuild and the CI config layer
Issue: #16
Status: closed
Labels: enhancement
Body:
## Problem

The bundled `delphi-dccbuild.ps1` exposes a `-NoConfig` switch (dcc32
`--no-config`) that skips auto-loading `<RootDir>\bin\dcc32.cfg`. This matters
when a toolchain's cfg carries actively wrong entries -- stale or incorrect
`-U`/`-I` library paths or options, not merely a nonexistent dir. With
`-NoConfig`, units and includes resolve only from the paths the caller supplies.

Today `Invoke-DelphiBuild` has no parameter for it, so neither direct callers
nor config/YAML-driven CI (`Invoke-DelphiCi`) can request it. This is the first
real use of the DCCBuild engine, so the option needs to be reachable.

## Proposed

Plumb `-NoConfig` with full parity to the other DCCBuild-only build options
(`Namespace`, `IncludePath`):

- `Invoke-DelphiBuild`: add `[switch]$NoConfig`; forward as `-NoConfig` to the
  build args; reject for the MSBuild engine (MSBuild has no dcc32.cfg) with a
  clear error, mirroring the Namespace/IncludePath guards.
- `Invoke-DelphiCi`: add `[switch]$NoConfig` (Run parameter set); record as an
  override; forward per build job to `Invoke-DelphiBuild`.
- `Get-DelphiCiConfig`: add `[switch]$NoConfig`; record as an override.
- `Resolve-DelphiCiConfig`: add `noConfig = $false` to the build built-in
  defaults; map the CLI override into the build layer as a scalar bool (no `!`
  array suffix).
- `schemas/delphi-ci.schema.json`: add a boolean `noConfig` property to
  `buildConfig` (default false, DCCBuild-only note) and reference it in the
  action-level and job-level build blocks.
- Docs: note `noConfig` in the DCCBuild-only section (README + Get-DelphiCiConfig).

`Invoke-BuildPipeline` needs no change -- its flat-token to splat conversion
already forwards a valueless `-NoConfig` switch correctly (issue #15).

## Acceptance criteria

- [ ] `Invoke-DelphiBuild -BuildEngine DCCBuild -NoConfig` forwards `-NoConfig` to the bundled tool
- [ ] `Invoke-DelphiBuild -BuildEngine MSBuild -NoConfig` throws a clear DCCBuild-only error
- [ ] A build job with `noConfig: true` in a config file reaches `Invoke-DelphiBuild` with the switch set
- [ ] `Invoke-DelphiCi -NoConfig` (CLI) propagates to build jobs
- [ ] The schema validates `noConfig` at both action and job level and rejects a non-bool
- [ ] Default (omitted) behavior is unchanged: dcc32.cfg still auto-loads

Title: Integrate bundled delphi-format tool with Invoke-DelphiFormat wrapper

Status: closed
Labels: enhancement
Body:
Wire the newly bundled `source/bundled-tools/delphi-format.ps1` into the CI
module the same way the other bundled tools are integrated, and expose a
public `Invoke-DelphiFormat` command.

## Background

`delphi-format.ps1` (tool version 0.6.1) is a Delphi source formatter
orchestrator with pluggable engine support (RAD Studio `formatter.exe` and
`radFormatter.exe`). It already implements the standard bundled-tool contract:
the `-Version -Format json` API, structured `-Json` / `-PassThru` output, a

Scope: full module integration + public wrapper. This ticket does NOT add a

### Registry: source/Private/Get-BundledToolInfo.ps1

Add an entry to `$toolDefs`:

    [PSCustomObject]@{ FileName = 'delphi-format.ps1'; SupportsVersionApi = $true }

`delphi-format` supports `-Version -Format json`, so the subprocess version
probe path applies. This raises the bundled-tool count from 8 to 9, which
breaks the hard-coded `@($info).Count | Should -Be 8` assertion in
`Invoke-DelphiCi.VersionInfo.Tests.ps1` -- update it to 9.

### Public command: Invoke-DelphiFormat

New `source/Public/Invoke-DelphiFormat.ps1`, modeled on
`Invoke-DelphiClean.ps1`, using the established `<Action><Param>` naming

`Tool`, `Message`, `ProjectFile`). Use `[CmdletBinding(SupportsShouldProcess)]`
and forward `-Check` when the caller requests audit-only.

Parameters (forwarded to the corresponding delphi-format.ps1 params):

- `-FormatExcludeDirectoryPattern` -> `-ExcludeDirectoryPattern` (string[])
- `-FormatEncoding` -> `-Encoding`
- `-FormatCreateBackups` (switch) -> `-CreateBackups`
- `-FormatOutputLevel` -> `-OutputLevel` (ValidateSet `detailed`, `summary`, `quiet`; default `detailed`)
- `-FormatConfigFile` -> `-ConfigFile`
- `-FormatCheck` (switch) -> `-Check` (audit-only; non-zero exit when files need formatting)

### Manifest: source/Delphi.PowerShell.CI.psd1

- Add `Invoke-DelphiFormat` to `FunctionsToExport`.
- Extend the module `Description` to list delphi-format among the bundled tools.

Title: Add a Format/FormatCheck step to the Invoke-DelphiCi pipeline
Issue: #18
Status: closed
Labels: enhancement
Body:
Wire the bundled `delphi-format` tool into the `Invoke-DelphiCi` pipeline as a
first-class `Format` action, so formatting (and audit-only format checking) can
run as part of a CI run driven by `delphi-ci.json`. This is the deferred
follow-up to #17, which added the standalone `Invoke-DelphiFormat` wrapper and

#17 integrated `delphi-format` as a bundled tool and exposed

cannot currently run formatting; only direct `Invoke-DelphiFormat` calls can.

## Concrete changes

Follow the same pattern used for the Clean and Codesign actions:

- `source/Public/Invoke-DelphiCi.ps1` -- add `Format` to the steps/dispatch;
  collect the Format* CLI overrides; dispatch to `Invoke-DelphiFormat` per job.

- `README.md` / examples -- document the Format action and a `delphi-ci.json`

- The `-FormatCheck` gate is the natural CI use: a Format job with `check: true`

  how a lint/verify step behaves. Confirm how a failing Format-check job maps to

- Reuse the `Invoke-DelphiFormat` wrapper rather than re-implementing arg
  forwarding, so the pipeline and direct-call paths stay in sync.

Acceptance criteria:
